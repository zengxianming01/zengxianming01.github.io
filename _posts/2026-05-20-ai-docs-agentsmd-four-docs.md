## 第1章 AGENTS.md：写给 AI 的项目规则

### 1.0 本章你会学到什么

这一章要把一个很多人嘴上会说、实际上没写明白的东西讲透：AGENTS.md。它不是普通项目介绍，也不是给人看的 README 替身，而是写给 Codex 的项目规则入口。

学完这一章，大家应该知道 AGENTS.md 解决什么问题、一个好用的 AGENTS.md 应该包含哪些信息、它和 README 的边界在哪里，以及为什么它比临时口头提醒稳定得多。

---

### 1.1 AGENTS.md 是写给 Codex 的规则

README 的读者主要是人，AGENTS.md 的第一读者是 Codex。这个区别一旦没讲清楚，后面整章都会写歪。

给人看的文档，往往更重背景介绍、项目故事、使用说明。
写给 Codex 的规则文件，重点应该是：这个项目怎么运行、哪些目录能动、哪些目录别动、改代码要遵守什么规范、执行任务前先看什么、哪些命令是安全的。

所以 AGENTS.md 的语言应该尽量直接、明确、可执行。不要写太多空话，例如「请高质量完成任务」「请注意代码优雅」。这种话对人有鼓励作用，对 Codex 的约束作用很弱。

---

### 1.2 一个好用的 AGENTS.md 的五个要素

![AGENTS.md 五要素示意](/images/20260520-ai-docs-20260521094957.png)

一个真正有用的 AGENTS.md，至少要回答五个要素：

1. **这个项目是做什么的**
2. **怎样启动、测试、构建**
3. **哪些目录或文件是高风险区域**
4. **代码规范和协作规则是什么**
5. **如果任务不明确，应该先看哪些文件**

如果这五个问题都没写清楚，Codex 很容易在项目里靠猜。它猜得准一次，不代表下次也准。AGENTS.md 的意义，就是把「靠猜」变成「有规则可循」。

---

### 1.3 为什么它比临时口头提醒更稳定

![AGENTS.md vs 口头提醒稳定性对比](/images/20260520-ai-docs-20260521095031.png)

很多人会在对话里一遍遍提醒 Codex：「别动这个目录」「先跑测试」「不要改接口名」。

这种提醒偶尔有用，但稳定性很差，因为任务一多、会话一长、上下文一换，就容易丢。把这些规则写进 AGENTS.md，就相当于把团队共识变成了项目环境的一部分。只要 Codex 进入这个项目，就能读到同一份规则，不需要每次靠人再说一遍。

对长期项目来说，这不是提高一点体验，而是决定它会不会越用越稳。

---

### 1.4 根目录规则、子目录规则如何配合

![根目录与子目录规则配合示意](/images/20260520-ai-docs-20260521095052.png)

AGENTS 规则不一定只有一层：

- **根目录规则**：适合写全项目共通约束，例如技术栈、常用命令、整体协作方式
- **子目录规则**：适合写某个模块自己的特殊说明

按照 Codex 官方文档，子目录里还可以有更具体的覆盖规则，这让大型项目更容易管理。因为一个仓库里的前端、后端、脚本目录、文档目录，往往不是同一种工作方式。

> **根目录规则负责定基线，子目录规则负责讲例外**

---

### 1.5 第一次写 AGENTS.md 时最容易写错什么

![AGENTS.md 常见错误示意](/images/20260520-ai-docs-20260521095110.png)

新手第一次写 AGENTS.md，最容易犯三个错：

1. **写成项目宣传页**，只讲背景，不讲规则
2. **写得太空**，例如「请保持代码整洁」，没有具体做法
3. **写得太长太散**，真正关键的规则反而埋没在大段废话里

一个更稳的做法是：**先写最小版**。先把启动命令、测试命令、危险目录、编码规范、任务前必读文件写清楚。等项目跑顺了，再慢慢补细节。

---

#### AGENTS.md 模板

##### 模板 A：通用项目（推荐起步模板，< 50 行）

```
# AGENTS.md

## 项目概述
这是一个 [项目名称]，使用 [技术栈] 构建。

## 命令
- 安装依赖：`npm install`（优先使用 pnpm）
- 开发模式：`npm run dev`
- 运行测试：`npm test`
- 代码检查：`npm run lint`
- 构建：`npm run build`

## 项目结构
- `src/app/` - 页面路由
- `src/components/` - 可复用组件
- `src/lib/` - 工具函数和配置
- `src/types/` - TypeScript 类型定义

## 代码规范
- 使用 TypeScript，避免 any 类型
- 组件使用函数式 + Hooks，不使用 Class 组件
- 文件命名使用 kebab-case（如 `user-profile.tsx`）
- 每个新函数都要写单元测试

## 注意事项
- 修改 JS/TS 文件后必须运行 `npm test`
- 添加生产依赖前先确认
- 不要修改 `migrations/` 目录下的已有文件
```

##### 模板 B：全局配置（放在 `~/.codex/AGENTS.md`）

```
# 全局工作约定

## 通用偏好
- 优先使用 pnpm 安装依赖
- 修改 JavaScript 文件后始终运行 npm test
- 添加新的生产依赖前先征求确认
- 提交消息使用中文

## 代码风格
- 使用 2 空格缩进
- 字符串使用单引号
- 行尾不加分号（如果项目 ESLint 配置允许）

## 文档偏好
- 注释用中文
- README 用中文编写
- 函数注释使用 JSDoc 格式
```

##### 模板 B+：全局规则进阶版

```
# Global rules for codex

## Operating principles
- Prefer small, reviewable diffs. Avoid sweeping refactors unless explicitly requested.
- Before editing, identify the file(s) to change and state the plan in 3-6 bullets.
- Never invent APIs, configs, or file paths. If unsure, search the repo first.
- Keep changes consistent with existing style and architecture.

## Safety and secrets
- Never paste secrets, tokens, private keys, .env values, or credentials into code or logs.
- If a task requires secrets, ask me to provide them via environment variables.
- Do not add analytics, telemetry, or network calls unless I ask.

## Code quality bar
- Add or update tests for behavior changes when the project has tests.
- Prefer type safety and explicit error handling.
- Add comments only when the intent is non-obvious.

## Build and run etiquette
- If you need to run commands, propose the exact command and why.
- When you make changes that may break build, run the fastest relevant check first.

## Output formatting
- For code changes: include a short summary + list of files changed.
- For debugging: include hypotheses, experiments run, and the minimal fix.

## My preferences
- I like concise explanations, concrete steps, and copy-pastable commands.
- Default language for explanations: Chinese.
```

### 1.6 本章小结

AGENTS.md 的价值，不在于文件名本身，而在于它把「反复口头提醒」变成「稳定可执行的项目规则」。写得清楚，Codex 才会越来越像靠谱同事，而不是每次都重新适应项目。

## 第2章 PLAN.md：把大任务拆成可执行步骤

### 2.0 本章你会学到什么

这一章要把一个特别重要、但最容易被写空的概念讲实：PLAN.md 施工蓝图。它不是一句「先做规划」的漂亮话，而是把大任务拆成可执行步骤的方式。

学完这一章，就能知道为什么大任务必须先拆再做、一个好的施工蓝图应该包含什么，以及怎样让 Codex 参与拆解，而不是直接把一个模糊大任务扔给它。

---

### 2.1 深度原理：为什么大任务必须先拆再做？

AI 并不是「理解」了你的需求，它是在预测下一个字符。

- **上下文偏移（Drift）**：当任务太大（如「做一个商城」），对话轮次变多，AI 会逐渐忘掉开头的约束
- **概率累积错误**：如果一步任务包含 10 个逻辑点，AI 每点出错概率是 5%，那整步成功的概率只有 $0.95^{10} \approx 60\%$。如果拆成 10 步，每步只做一件事，成功率接近 100%
- **PLAN.md 的本质**：它是你与 AI 之间的**「施工契约」**，是防止 AI 在执行过程中因为「脑补」而跑偏的锚点

---

### 2.2 PLAN.md 解决什么问题

![PLAN.md 解决问题示意](/images/20260520-ai-docs-20260521100215.png)

AI 没有真正的「逻辑大脑」，它本质上是一个概率预测引擎。

- **上下文丢失（Lost in the Middle）**：当对话变长，AI 对中间部分的记忆力会断崖式下降
- **熵增效应**：每生成一行代码，错误的可能性就会累积。没有蓝图，AI 就像在迷雾中开车，每走一步方向偏 1°，走一公里就彻底南辕北辙了
- **PLAN.md 的本质**：它是 AI 的外部显存。它强行把「不确定」的未来变成了「确定」的离散步骤

PLAN.md 解决的核心问题：

- ✅ 防止需求漂移：锁定目标，防止 AI 边做边改需求
- ✅ 提供检查点：每完成一步都可以验证
- ✅ 支持长时间运行：即使 Codex 运行数小时，也能保持方向
- ✅ 人类可审查：你可以在 Codex 动手之前审查和修改计划

例如：「做一个智能体对话平台」听起来像一句完整需求，实际上里面可能包含产品设计、前端界面、后端接口、鉴权、部署、测试、文档、演示等很多层。没有蓝图，任务一开始就容易乱冲。

### 2.3 结构化你的蓝图：PLAN.md 的四个核心模块

![PLAN.md 四个核心模块示意](/images/20260520-ai-docs-20260521100243.png)

一个能落地的 PLAN.md 应当像一份施工说明书，而非产品愿景图。建议采用以下标准模板。

---

### 2.4 核心技巧：如何「切」任务才叫好？

![任务原子化拆解示意](/images/20260520-ai-docs-20260521100317.png)

拆解任务时，遵循 **「Atomicity」（原子化）** 原则。

**错误拆解（太虚）：**
- Step 1: 开发后端逻辑
- Step 2: 连接数据库

**专业拆解（Codex 可执行）：**
- Step 1: 在 /models 下创建 User.ts 实体类，包含 email 和 password 字段
- Step 2: 编写数据库迁移脚本，初始化 users 表
- Step 3: 实现 POST /api/register 接口，并验证字段非空

> **金句**：如果一个步骤大到让 Codex 一次性生成了超过 100 行代码，那么这个步骤就该继续拆。

---

### 2.5 让 Codex 变成你的「架构审计师」

![Codex 架构审计示意](/images/20260520-ai-docs-20260521100346.png)

不要直接把任务扔给它，要利用它的多维发散能力来补全你的思维盲点。

推荐的引导词（Prompting）：这种方式能让 Codex 帮你发现——原来做「上传功能」前，还得先配置 S3 的权限。

---

### 2.6 避坑指南：识别「伪拆解」

![伪拆解避坑指南示意](/images/20260520-ai-docs-20260521100432.png)

教学中要警惕这三种看起来很美、实则无效的计划：

1. **「时间线陷阱」**：只有 1, 2, 3 顺序，没有依赖关系。一旦第 2 步卡住，AI 会盲目执行第 3 步，导致代码全是 Bug
2. **「黑盒步骤」**：写着「实现 AI 核心逻辑」。这对 Codex 来说等于没说。必须细化为「调用 OpenAI API」、「处理流式返回」、「格式化 JSON」等具体动作
3. **「缺乏状态感」**：好的 PLAN.md 应该带状态勾选框——`[✅] 已完成`、`[/] 进行中`、`[ ] 待开始`。PLAN.md 是活的，执行过程中随时根据反馈修改它

---

### 2.7 深度思考：为什么 PLAN.md 是 Codex 进阶的标志？

![PLAN.md 进阶标志示意](/images/20260520-ai-docs-20260521100454.png)

在 Codex 的世界里：

- **初级用户**：直接写需求 → 报错 → 骂 AI 笨
- **中级用户**：写需求 → 得到 PLAN → 确认 PLAN → AI 执行
- **高级用户**：引导 AI 写 PLAN → 质疑并优化 PLAN → 驱动 AI 模块化执行

---

### 2.8 本章小结

施工蓝图不是文档装饰，而是大任务能不能落地的前提。先拆目标、边界和验收标准，再让 Codex 参与分解步骤，任务才不容易越做越散。

## 第3章 四文档法则构建项目框架

### 3.0 本章你会学到什么

这一章要处理的是「项目协作文档怎么配合」的问题。这里最容易误导大家的地方，是把这几类文档讲成官方强制格式。实际上，它们更像是一套项目方法论，用来把复杂任务拆开，让协作更稳。

学完这一章，大家应该知道这些文档各自负责什么、为什么大任务不能只靠聊天记录推进，以及小团队怎样建立一套最小可用的文档链路。

---

### 3.1 为什么要分四个文件？

![四文档分文件原因示意](/images/20260520-ai-docs-20260521100551.png)

如果把所有信息塞进一个文件，AI 会因为干扰信息太多而导致「推理降级」。

![四文档非强制格式示意](/images/20260520-ai-docs-20260521100625.png)

**这四类文档不是官方强制格式。** agent.md、plan.md、implement.md、documentation.md 不是 Codex 官方强制要求的四件套。它们是很多团队在实际协作里总结出来的做法。

为什么还值得讲？因为它们命中了真实问题。任务一复杂，单靠聊天记录很难持续推进。今天说过什么、明天要做什么、谁负责哪一段、已经做到哪一步，很快就会散。

所以这一章真正要讲的，不是「官方要求你这样命名」，而是「为什么项目方法需要分层记录」。

---

### 3.2 implement.md：最被低估的「黑匣子」

![implement.md 黑匣子示意](/images/20260520-ai-docs-20260521100709.png)

这是本章的灵魂。很多人不写这个。

- **原理**：AI 不知道你刚才手动改了哪个变量名
- **实操**：每次 Codex 改完代码，或者你手动调通了一个 Bug，立刻在 implement.md 写一行：`2026-04-18: 将数据库连接池从 10 改为 50，解决了高并发下的 Timeout 问题`
- **价值**：下次新开对话时，把这个文件一扔，AI 立刻知道项目的最新状态

**为什么一个大任务不能只靠聊天记录推进：**
聊天记录适合临时沟通，不适合长期承载项目结构。一个任务如果跨了几天、几个人、几个模块，再长的聊天线程也会变得很难回看。

大任务需要把不同层面的信息拆开：决策写进计划，执行写进实现记录，结果写进文档沉淀，角色和边界写进 agent 说明。这样每个文件只承担一种责任，后面复盘时也清楚。

---

### 3.3 agent、plan、implement、documentation 各自负责什么

![四文档各自职责示意](/images/20260520-ai-docs-20260521100729.png)

可以把这四类文件理解成四种不同的问题：

> - **agent.md** 回答的是「谁在这个项目里扮演什么角色、遵守什么边界」
> - **plan.md** 回答的是「这件事打算怎么拆、先做什么后做什么、验收标准是什么」
> - **implement.md** 回答的是「已经怎么做了、改了哪里、遇到了什么问题」
> - **documentation.md** 回答的是「最后沉淀给谁看、以后怎么复用」

一旦分清这四个问题，就不会再把「计划文件里写实现细节」「实现记录里写背景介绍」全混在一起。

---

### 3.4 建立协作链路

不要一上来就做很重的文档体系，最小可用链路就够了。可以从一条简单流程开始：

```
需求 → plan.md（先写目标和步骤）→ implement.md（边做边记）→ documentation.md（做完沉淀）
```

如果项目角色复杂，再补 agent.md 来界定分工和规则。

这套链路的重点，不是文件名，而是「每类信息放在固定位置」。固定了位置，团队协作成本就会下降。

---

### 3.5 这些文档什么时候该轻，什么时候该重

![文档轻重权衡示意](/images/20260520-ai-docs-20260521100756.png)

如果只是一个半天能做完的小任务，不需要每个文件都建。

任务越复杂、越跨人、越跨时间，这套文档越值得补齐。

判断标准可以很简单：
- 如果这个任务明天回头看时，你担心自己忘了为什么这样做——**那就该写**
- 如果这个任务会交给别人接手——**那更应该写**
- 如果这个任务只是随手试试、失败也无所谓——**那就可以轻一点**

好的文档体系应该减轻混乱，而不是制造更多形式主义。

---

### 3.6 本章小结

这几类文档的价值，不在于名字，而在于把复杂任务拆成不同层次的记录。只靠聊天推进大任务，迟早会乱；把计划、执行、沉淀分开，项目才容易稳。

**使用方法总结：**

```bash
/init  # 生成 AGENT.md
```

然后在对话框输入：
1. 在 plan.md 里写目标、范围、步骤和验收标准
2. 执行过程中在 implement.md 里记录关键改动
3. 任务结束后在 documentation.md 里沉淀对外可复用的内容

---

## 第4章 产品文档与四文档法则的协同

### 4.0 本章你会学到什么

- PRD 与四文档的本质区别：为什么不能直接把产品文档当成 Prompt
- 映射机制：如何把 PRD 的功能点精准拆解到 agent、plan、implement 和 doc 中
- 动态对齐：当产品需求变更时，如何不推倒重来，只微调四文档

---

### 4.1 维度差异：产品文档（外部需求）vs 四文档（内部执行）

![PRD 与四文档维度差异示意](/images/20260520-ai-docs-20260521100903.png)

我们要先理解两者的生态位：

- **PRD（Product Requirement Document）**：回答的是为了解决谁的什么问题，我们要提供什么功能。它充满商业逻辑、用户故事和交互愿景
- **四文档法则**：回答的是「为了实现这个功能，AI 应该扮演谁、走哪几步、记住什么、最后交付什么」

如果你把 PRD 直接扔给 Codex，它会陷入「认知过载」，因为它试图同时理解你的商业逻辑、代码架构和样式细节。四文档的作用就是「降压」，将 PRD 里的宏大叙述降维成可执行的切片。

---

### 4.2 协同映射：从 PRD 到四文档的转化路径

![PRD 到四文档转化路径示意](/images/20260520-ai-docs-20260521100940.png)

当拿到一份 PRD 时，你需要通过以下四个「转换插头」进行映射：

#### 4.2.1 PRD 风格/限制 → agent.md（规则对齐）

- **PRD 描述**：「界面要极简、专业，适合金融用户。」
- **agent.md 转化**：「UI 规范：使用 Tailwind 灰度色系，禁止使用高饱和度色彩；交互：所有金融数值必须保留两位小数并增加千分位符。」
- **原理**：将感性的产品调性转化为理性的代码约束。

#### 4.2.2 PRD 功能列表 → plan.md（路径拆解）

- **PRD 描述**：「支持用户上传 CSV 并自动生成可视化图表。」
- **plan.md 转化**：
  - Step 1: 集成 Lucide-react 图表库
  - Step 2: 编写后端解析 CSV 的逻辑
  - Step 3: 建立数据到图表的映射函数
- **原理**：将「用户动作」转化为「技术流水线」。

#### 4.2.3 PRD 逻辑细节/异常处理 → implement.md（记忆存档）

- **PRD 描述**：「如果网络波动，必须有断点续传功能。」
- **implement.md 转化**：记录当前断点续传的实现方案（如使用 localStorage 记录偏移量）
- **原理**：记录那些 PRD 里一句话带过，但代码实现里非常复杂的「坑」。

#### 4.2.4 PRD 验收标准 → documentation.md（交付标准）

- **PRD 描述**：「最终交付物应包含 API 文档，方便三方接入。」
- **documentation.md 转化**：定义生成的 Swagger/OpenAPI 格式规范

---

### 4.3 第一步：让 Codex 帮你把「灵感」捏成「PRD」

![灵感转化为 PRD 示意](/images/20260520-ai-docs-20260521101005.png)

别觉得写 PRD 是产品经理的事。在 AI 时代，PRD 是为了对齐你和 AI 的大脑。你的想法往往是散的，而 Codex 擅长结构化。

**操作逻辑**：你提供「灵魂（核心功能）」，Codex 提供「肉身（完整逻辑）」。

**原理**：这一步不是为了写文档而写文档，而是利用 Codex 帮你排雷。它会提醒你那些被你忽略的细节（比如授权提醒、缓存机制），这些细节如果不在 PRD 里定死，后面写代码时 AI 就会疯狂瞎猜。

---

### 4.4 第二步：桥接——将 PRD 自动化拆解为「四文档」

![PRD 拆解为四文档示意](/images/20260520-ai-docs-20260521101114.png)

有了 PRD，千万不要直接开干！PRD 是给人类看的「愿景」，AI 吞不下这么大块的肉。

你需要把 PRD 丢进一个**「转化器」**，输出四文档。

![PRD 转化器示意](/images/20260520-ai-docs-20260521101130.png)

> **金句**：PRD 是「我要去哪」，四文档是「我每一步脚踩在哪」。

---

### 4.5 第三步：协同演进——当需求变动时的「版本同步」

![需求变更版本同步示意](/images/20260520-ai-docs-20260521101149.png)

这是最考验逻辑的地方：如果 PRD 变了，代码怎么跟上？

很多人的错误做法是：在对话框里对 Codex 说「那个功能改一下」。这样做的后果是，你的 PRD 是旧的，代码是新的，AI 的上下文是乱的——项目离崩盘不远了。

**逻辑闭环流（The Sync Loop）：**

1. **改源头**：先在 PRD 里修改那个功能点
2. **更新执行层**：让 Codex 根据 PRD 的变动，同步更新 plan.md 和 agent.md
3. **刷新状态**：重启对话，将更新后的四文档发给 Codex

**为什么要「重启对话」？**

因为 AI 的对话历史有**「逻辑惯性」**。如果你不重启，它的大脑里还残留着旧需求的残影。通过更新四文档并重开对话，你相当于给了 AI 一个「干净且最新的快照」。

---

### 4.6 第四步：反向校验——利用四文档压测 PRD

![四文档反向校验 PRD 示意](/images/20260520-ai-docs-20260521101219.png)

逻辑的最高层级是：让执行层反哺决策层。

当你把 PRD 转化成 plan.md 之后，问 Codex 拆解步骤是否合理。

**原理**：Codex 在拆解步骤时，会发现 PRD 里逻辑不自洽的地方。这时候，它是你的**「首席技术审计师」**。在代码写出来之前，先把 PRD 里的 Bug 给修了。

---

### 4.7 本章小结：文档不是负担，是 AI 的「外挂存储」

![文档是 AI 外挂存储示意](/images/20260520-ai-docs-20260521101252.png)

- 用 Codex 补全你的思维漏洞（生成 PRD）
- 将高维愿景降维成施工蓝图（转化四文档）
- 需求变更时，通过「文档同步 + 重启」保持对齐
- 利用拆解过程反向审计需求的合理性

> **一句话总结**：PRD 负责想清楚，四文档负责做清楚，两者协同，才能让 Codex 真正成为你手中那台永不跑偏的精密机床。
